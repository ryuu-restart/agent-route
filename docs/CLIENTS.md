# 客户端适配原则

默认规则接入见 [AGENTS](../AGENTS.md)。使用者的 Agent 按目标设备实际运行的客户端和核心版本选择格式、配置入口和验证方式。

<a id="scope"></a>

## 接入范围

先确认用户要改的是哪一处配置，以及要覆盖哪些流量。

| 目标 | 做法与结论范围 |
| --- | --- |
| Windows 或 Mac 的现有客户端接入规则 | 默认范围。沿用当前接管方式，验证该客户端实际接管的流量。DNS 和 WebRTC 的浏览器检测按需进行 |
| 明确要求完整设备接入 | 按 [TUN 前置检查](#tun-required)和[逐项验收](DNS-WEBRTC.md#acceptance)验证获准的流量、DNS、WebRTC 和持久化 |
| VPS 只作节点 | 在电脑上负责分流的客户端接入。VPS 继续作为原有代理出口 |
| 获准在服务器或网关上接入 | 改实际执行分流的配置。结论覆盖该核心接管的流量，直连使用该服务器或网关的出站网络 |
| 仅同步或分发规则文件 | 按[同步工具](SYNC.md)核对文件更新和校验 |

只接规则时，向用户说明哪些应用实际经过该客户端。VPN 只有应用或 IP 网段分流时，说明域名或拦截能力的缺口。修改远程服务器前，先确认断开 SSH 后仍能通过独立入口恢复。

<a id="tun-required"></a>

## TUN 前置检查

完整设备接入要求 TUN 或经核实的等效系统隧道，包括客户端对应的增强模式或系统 VPN 接管能力。检查运行状态、系统路由以及目标应用的流量和 DNS 路径，IPv6 单独验收。用实际连接取证。

尚未启用时，按实际版本给使用者开启步骤与恢复方法，待其启用并确认后再做完整接入。系统代理、浏览器代理或 mixed 入站的结果只覆盖实际接管的应用。无法确认全设备接管时报告该项待验证，或由用户选择按[默认规则范围](#scope)接入。规则模式和 DNS 路径分别核实。

IPv4 接管成立就继续接入。IPv6 没被接管时单独记失败并说明影响：直接走 IPv6 的连接会绕过代理。处理方式由用户选：开启客户端支持的 IPv6 接管，或接受限制（最多部分完成）。关闭 IPv6 只能由用户决定，不能当默认修复。

TUN 和系统代理可以同时开。这时网页可能走系统代理、WebRTC 的 UDP 走 TUN，要分别取证；连接记录里的入站类型能看出走了哪条路径。

## 资源与规则语义

[机器索引](https://raw.githubusercontent.com/ryuu-restart/agent-route/release/index.json)列出资源地址、格式及条目数，[清单](https://raw.githubusercontent.com/ryuu-restart/agent-route/release/manifest.json)记录发布信息与摘要。公开读取无需凭据。

| 客户端 / 核心 | 使用格式 | 资料入口 |
| --- | --- | --- |
| Mihomo 及其图形客户端 | `mihomo/<规则>.yaml`，域名与 IP 使用相应 behavior | [规则集](https://wiki.metacubex.one/config/rule-providers/)、[DNS](https://wiki.metacubex.one/config/dns/) |
| Surge / Shadowrocket | `surge/<规则>.list`，无策略列的 RULE-SET 文本 | [Surge 规则集](https://manual.nssurge.com/rules/ruleset.html)；Shadowrocket 目前没查到公开的官方配置手册，核对 App 内说明、[社区手册](https://github.com/LOWERTOP/Shadowrocket)（非官方）和实际能力，不直接照搬 Surge 字段 |
| sing-box 及其图形客户端 | `sing-box/<规则>.json`，source rule-set version 3 | [规则集](https://sing-box.sagernet.org/configuration/rule-set/)、[迁移说明](https://sing-box.sagernet.org/migration/) |

`<规则>` 为 private、reject、proxy、direct、cn-ip；地址前缀为 `https://raw.githubusercontent.com/ryuu-restart/agent-route/release/`。格式版本是实际兼容要求，不是文档装饰。旧格式公开地址继续保留，但新接入优先选择索引中的标准资源。来源是镜像或自建转换时，内容等效且刷新正常就保留，报告注明未核对发布代。

默认合并保留原有规则的优先级和最终兜底。适用的项目规则按 **private → reject → proxy → direct → cn-ip** 加在最终兜底之前。内网和国内类使用用户已有的直连策略，拦截类使用拦截策略，海外类使用该类流量现有的代理组。复用有效的同一规则引用。旧规则抢先命中时，说明具体冲突，由用户决定是否调整。

完整模板展示用户例外、节点地址、LAN 和 DNS 服务器路径优先的方案。合并时核对这些流量的实际去向，并将 FakeIP 池、TUN 接口等核心自有地址与真实 LAN 和中国 IP 分开判断。

`private` 为通用内网域名，`direct` 只含域名，`cn-ip` 只含公网中国 IPv4 / IPv6。保留精确域名和后缀的区别。域名进入中国 IP 兜底时须核对整组真实地址，混合国内外答案沿用原配置策略。Mihomo 的 `no-resolve` 跳过本条触发的解析，前序规则已经解析的地址仍可能命中。因此须检查合并后的完整顺序。无法保证时保留现有兜底，按[受限接入](#limited-integration)处理该项。sing-box 的 non-cn-ip 辅助集用于 DNS 判断，具体实现按版本确认。[Mihomo 匹配说明](https://wiki.metacubex.one/en/config/rules/#no-resolve)

<a id="baseline"></a>

## 版本与可选示例

先核对真实核心而非仅看 GUI 版本，再查对应版本的官方配置文档、迁移说明、程序帮助或配置 Schema。版本不同先确认能力，不直接要求升级或降级；没有可靠依据时报告不确定性。仅有社区资料时注明来源性质，并用实际检查与运行证据核实，不能写成官方已保证。

四套[完整示例及历史验证记录](../examples/README.md)仅供参考。示例支持的功能、验证版本和限制不等于整个项目的最低版本或未来兼容承诺。也可以不使用模板。

<a id="pitfalls"></a>

## 通用检查点

执行 Agent 根据现场能力决定如何实现和取证。默认规则接入按[接入流程](../AGENTS.md#3-确认分流生效)核对，完整设备接入按[逐项验收](DNS-WEBRTC.md#acceptance)判定。发现项目准则或示例有矛盾时，可使用[反馈入口](../AGENTS.md#issue-feedback)。

| 检查点 | 必须保持的准则 |
| --- | --- |
| 用户例外与规则顺序 | 在最终生效配置中验证优先级；中间编辑器、扩展或模块的保存顺序不能代替最终规则顺序。域名类例外（含订阅自带的域名规则）的解析去向同样保留：改动解析器设置前先核对它们原来用哪个解析器，按同一域名条件补齐 DNS 策略；表达不了时说明限制并由使用者选择 |
| 配置来源与持久化 | 区分原始配置、覆写、当前配置档和运行配置；按实际版本核实谁拥有最终值，订阅刷新后仍须成立 |
| DNS 全阶段路径 | 首次、备用、再次解析及出站绑定的解析器都遵守域名类别目标；业务直连不自动授权 DNS 直连，节点域名不经该节点所在的代理解析，本地解析标签不证明实际上游。域名类别来自域名规则（含用户例外），IP 规则和中国 IP 兜底不改变它 |
| 域名与核心自有地址 | 已知域名应按域名规则判断；裸 IP、嗅探和 FakeIP 是不同证据。FakeIP 池、TUN 接口等核心自有地址按运行配置的实际值核对，各地址族的来源可能不同，都不能命中真实 LAN 或中国 IP 兜底 |
| 证据与能力边界 | 单字段、单次探针、语法检查或另一设备的成功都不代表目标设备通过；不能保持目标时报告限制并由使用者选择 |

具体版本的来源、已知案例和系统命令保存在[可选证据](CLIENT-EVIDENCE.md)。按需查证，不把案例当作通用操作步骤。

<a id="config-check"></a>

## 配置检查

选用当前客户端真实支持的检查命令、配置检查器或导入校验；命令、路径和参数从实际帮助确认。检查候选文件及 GUI 最终生成的有效配置，不能只检查片段。检查或导出工具可能只解析部分段落：先确认它的输出或说明覆盖了待验证的规则、规则集和 DNS，未覆盖的部分记未做原生检查。无可用入口就注明未做原生检查，并明确可获得的导入、加载及运行证据。

配置语法通过不代表资源已加载、DNS 走向正确或设备已接管。资源、规则、DNS 等依赖应在应用前齐备；不能为了测试而另起未管理的代理或第二条 TUN。

<a id="where-changes-survive"></a>

## 配置持久化

**判定。** 分别识别**持久配置来源、生成或托管的运行副本、核心当前运行状态**，以及谁负责下次生成和启动配置。它们可能分属不同文件、进程或服务；文件写入成功、API 返回成功、规则已加载应分别记录，都不能单独证明已持久化。管理程序重新生成后，相应规则、规则集和 DNS 仍出现在运行配置中，这个位置才算持久化位置；订阅原文和主配置都可能只是生成器的输入或输出，其中的段落可能被丢弃。在用户授权且可恢复的条件下，经过适用的重新生成、订阅刷新和重启后，必要规则、DNS 策略及用户例外仍在实际运行状态中生效，持久化才算通过。只验证临时加载成功或未完成这些复查时，持久化记未验证；重新生成后改动丢失则记失败，不能用再次临时注入冒充持久化通过。

**约束。** 通过实际管理该配置的程序所支持的流程应用修改，使持久来源和后续生成结果一致；只修改中间副本或核心内存，可能在管理程序重新生成或恢复时被覆盖。保留用户例外，不让受管规则提前覆盖它们，也不让旧最终规则抢先命中。订阅由用户自建时，是否改生成端由用户决定。路径或权限检查拒绝请求时，先查明配置归属和受支持入口；不默认放宽目录权限、关闭路径检查或直接写受保护的托管副本。找不到可靠的持久化位置时，说明改订阅原文或另建本地配置的影响（同样按上述标准核对），取得用户选择；不要静默换配置来源。节点变化后，节点连接例外和引导解析也需重新核对。

**做法提示。** 可先确认配置是本地编辑、订阅生成、托管，还是由客户端每次连接时按自身骨架重新生成；再找该版本支持的持久覆写、扩展或模块机制，核对它是合并还是整段替换，以及实际规则顺序。具体使用 GUI、API 还是命令行由执行 Agent 按现场能力选择，不绑定某个按钮。版本案例见[可选证据](CLIENT-EVIDENCE.md#运行时加载与持久化的区别)。

<a id="limited-integration"></a>

## 能力不足与受限接入

托管配置或模块可能限制可用策略和排序。先按官方资料与现场检查确认限制；若无法保持规则语义，说明缺失能力和替代方案，取得用户选择。没有可靠方案或用户未接受限制时停止相关修改。

用户接受受限接入时，说明实际接入的资源、主配置承接的行为和缺失项。保留用户例外，并按[接入范围](#scope)核对对应的完成条件。完整设备接入还需验证适用的 TUN、DNS 和 WebRTC 目标。[Surge 模块手册](https://manual.nssurge.com/profile/module.html)提供了策略和排序受限的一个例子。

## 更新与验证责任

规则每日 UTC+8 06:30 计划构建，实际发布时间以清单为准。验证失败时保留旧发布。建议启用客户端自动刷新，核实资源已成功加载且非空。严格同代下载、校验与本地回退见 [SYNC](SYNC.md)。

项目测试覆盖规则与记录的示例。目标设备的加载、分流及刷新后表现由使用者的 Agent 核实，DNS 和 WebRTC 按获准范围另外取证。
